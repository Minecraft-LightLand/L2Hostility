# L2Hostility Design

System-level documentation of L2Hostility (Forge 1.20.1 / 47.4.0 / Java 17). This document explains
*how the systems work*: their logic and data flow. It is about architecture and flow, not about the
individual balance values (which live in the datapack configs and `LHConfig`).

Code references are `src/main/java/dev/xkmc/l2hostility/...` unless prefixed with `L2Library:`
(which means `/Users/arthur/git/mods_l2/L2Library/src/main/java/dev/xkmc/l2library/...`).

---

## 1. Overview

The mod makes hostile mobs harder over time by giving them a **level** and a set of **traits** with
ranks. The core loop is:

1. A hostile mob spawns. Its level is rolled from a difficulty formula.
2. The level is spent on **health** (attribute scaling) and on **traits** (a weighted random pool
   with cost, rank, and exclusion rules).
3. Traits modify the mob every tick and hook into the **damage pipeline** (`l2damagetracker`).
4. Killing mobs grows the player's personal difficulty and the chunk's local difficulty, so the
   world escalates as the player progresses.

Everything numeric and configurable flows through the **datapack config system** (section 3). The
mod ships default JSONs (generated by `runData` in `src/generated/resources`) that players/mods can
override with datapacks.

Key entry points:

- `init/L2Hostility.java` — mod entry, network channel, config-registry declarations, datagen hooks.
- `content/capability/` — Forge capabilities: `MobTraitCap` (per-mob), `ChunkDifficulty` (per-chunk),
  `PlayerDifficulty` (per-player).
- `content/logic/` — difficulty math, trait generation, equipment population, level editors.
- `content/config/` — the datapack config classes.
- `content/traits/` — the trait registry and trait implementations.
- `events/` — Forge event handlers that glue capabilities to gameplay.
- `editor/` — the in-game datapack editor.

## 2. Bootstrapping and registration

`init()` (L2Hostility.java:74) runs at mod construct time and registers, in order:

1. Content via Registrate: `LHBlocks`, `LHItems`, `LHTraits`, `LHEntities`, `LHMiscs`, `LHConfig`
   (the Forge config specs), `LHDamageTypes`, `LHEnchantments`, `LHEffects`.
2. `TraitGLMProvider` (global loot modifiers for trait drops).
3. The three capabilities (`MobTraitCap`, `ChunkDifficulty`, `PlayerDifficulty`).
4. `HostilityTriggers` (advancements).

The constructor additionally:

- Builds the Patchouli guide book.
- Registers `LHAttackListener` with `AttackEventHandler.register(4500, ...)` so the mod participates
  in the `l2damagetracker` attack pipeline.
- Registers gateway compat if `gateways` is loaded (`GatewayToEternityCompat`).

### 2.1 Network and config registries

`L2Hostility.HANDLER` is a `PacketHandlerWithConfig` (L2Library serial.config) on channel `main`.
It owns four packet types (MobCapSyncToClient, TraitEffectToClient, LootDataToClient,
ChunkCapSyncToClient) plus the **config sync** machinery. Five config types are declared on it
(L2Hostility.java:67-71):

| Field | name | class | contents |
|---|---|---|---|
| `DIFFICULTY` | `difficulty` | `WorldDifficultyConfig` | per-dimension/biome base difficulty, per-dimension/structure entity traits |
| `TRAIT` | `trait` | `TraitConfig` | per-trait cost/rank/level gates/weight |
| `TRAIT_EXCLUSION` | `trait_exclusion` | `TraitExclusion` | per-trait exclusion map (trait id → rate) |
| `WEAPON` | `weapon` | `WeaponConfig` | loot-table-style weapon/armor pools + enchant pools |
| `ENTITY` | `entity` | `EntityConfig` | per-entity spawn overrides (traits, items, level, scaling) |

### 2.2 Trait registry details

Traits are a custom Forge registry `LHTraits.TRAITS` (LHTraits.java:34), registered through
`LHRegistrate.regTrait(id, supplier, configFactory)` (init/entries/LHRegistrate.java:26). This
builds a `TraitBuilder` (init/entries/TraitBuilder.java) that:

- Registers the trait object into the `trait` registry.
- Registers a **matching item** (`TraitSymbol`) — the collectable trait token.
- Emits the trait's default `TraitConfig` into the `trait` config type via the builder's
  `TraitConfig` factory (`owner.addTraitConfig`, TraitBuilder.java:37).
- Optionally emits a `TraitExclusion` via the `.exclusion(...)` builder call
  (TraitBuilder.java:64-69).
- Registers lang keys (`lang()`, `desc()`).

`TraitConfig` also builds two per-trait *entity* tags (`<trait>_blacklist`, `<trait>_whitelist`,
TraitConfig.java:47-68) that datagen writes and `allows(...)` reads at runtime.

## 3. The datapack config system

All five config types share one pipeline provided by L2Library's `dev.xkmc.l2library.serial.config`
package. Understanding it is required to understand everything else.

### 3.1 File layout

`ConfigTypeEntry.asPath(id)` (ConfigTypeEntry.java:17) maps `(namespace, path)` to
`data/<ns>/<ns>_config/<name>/<path>.json` — `config_path` is always
`<namespace> + "_config"` (PacketHandlerWithConfig.java:57). Example:

```
data/l2hostility/l2hostility_config/trait/grenade.json
data/l2hostility/l2hostility_config/trait_exclusion/grenade.json
data/l2hostility/l2hostility_config/difficulty/overworld.json
```

### 3.2 Default emission (runData)

`LHConfigGen extends ConfigDataProvider` (init/data/LHConfigGen.java) is added to the datagen in
`gatherData`. Its `add(Collector)` is called by `ConfigDataProvider.run`
(ConfigDataProvider.java:33), which serializes each entry with `JsonCodec.toJson` and saves it via
`DataProvider.saveStable`.

Every `TraitConfig`/`TraitExclusion` the trait registrations registered is emitted transparently:
`LHConfigGen.add` first dispatches `L2Hostility.REGISTRATE.CONFIGS.forEach(e -> e.accept(collector))`
(LHConfigGen.java:52). Remaining defaults (overworld/nether/end difficulty, boss entities, weapon
pools, per-mod compat) are added explicitly with `collector.add(type, id, config)`.

`Collector.add` (ConfigDataProvider.java:54) is the single funnel:
`map[type.asPath(id)] = new ConfigEntry(type, id, config)`.

### 3.3 Loading and merging

On every datapack reload the `ConfigReloadListener`
(PacketHandlerWithConfig.java:89) scans `data/*/<ns>_config/`. For each json:

1. The **first path segment** (before `/`) selects the config type by name.
2. The rest becomes `namespace:path`, which is stored as the config's **id**
   (`config.id = k`, PacketHandlerWithConfig.java:122) and keyed in `type.configs`.

Because a datapack may replace a file, several raw configs can exist for the same type. Access is
always through the **merged** view:

- `ConfigTypeEntry` construction calls `channel.addCachedConfig(name, cls)`, creating a
  `MergedConfigType` (ConfigTypeEntry.java:14).
- `getMerged()` → `MergedConfigType.load()` (MergedConfigType.java:13) lazily merges **all loaded
  configs of that type** into one object and caches it.
- `MergedConfigType.afterReload()` nulls the cached result, so the next access re-merges.

Merging semantics come from per-field `@ConfigCollect(CollectType)` annotations (ConfigMerger.java):

| CollectType | behavior |
|---|---|
| `OVERWRITE` | the last datapack layer wins (whole field replaced) |
| `COLLECT` | concatenated into one list (used by `WeaponConfig` pools, `EntityConfig.list`) |
| `MAP_COLLECT` | per-key merge; `Map<K,List<V>>` concatenates, `Map<K,Map>` does putAll |
| `MAP_OVERWRITE` | `putAll`, last layer wins per key (used by `WorldDifficultyConfig` maps) |

After merging, `postMerge()` runs on the result — `EntityConfig` rebuilds its entity-type cache and
condition map there (EntityConfig.java:38-50).

### 3.4 Server → client sync

`MergedConfigType.beforeReload` records the server-side configs into `handler.configs`. On datapack
sync (`PacketHandlerWithConfig.onDatapackSync`, triggered by Forge's `OnDatapackSyncEvent`) the
whole `configs` list is sent to clients in a `SyncPacket` (single message to everyone on login, or
per-player). The client deserializes and rebuilds its own merged views, so client-side rendering
(e.g. Jade/JEI) sees identical values.

### 3.5 Runtime access

- `L2Hostility.<TYPE>.getMerged()` — the merged object (most common).
- `getEntry(ResourceLocation id)` — a single config by id (used per-trait by `MobTrait.getConfig()`
  and `getExclusion()`).
- `getAll()` — every raw config.

Per-mob lookups that want a *merged-per-entity* answer are handled inside the config classes, e.g.
`EntityConfig.get(EntityType)` returns the merged `Config` for that entity (cached server-side).
`WorldDifficultyConfig.get(...)` and `getConfigCache` (next section) resolve dimension/structure
default traits lazily.

## 4. Difficulty and mob level

### 4.1 Data flow (who computes the level)

A spawn goes through this chain:

```
MobSpawnEvent.FinalizeSpawn  (CapabilityEvents.initMob)
        └─ ChunkDifficulty.at(level, pos)              // find the chunk capability
             └─ MobTraitCap.init(level, le, chunkDiff) // builds the collector, rolls lv, fills traits
                  └─ TraitManager.fill(cap, le, traits, MobDifficultyCollector)
                       └─ TraitGenerator.generateTraits(...)
```

If the spawn event doesn't fire the init (e.g. the chunk cap was unavailable), `MobTraitCap.tick`
retries at the next tick (MobTraitCap.java:267-270).

`MobDifficultyCollector` (content/logic/MobDifficultyCollector.java) is the accumulator. Its fields
are folded in from many sources, each `acceptConfig` multiplying/adding its contribution:

| source | what it contributes | code |
|---|---|---|
| `EntityConfig.Config.difficulty` | min/base/scale/variation/apply-chance/trait-chance/suppression | `init` acceptConfig (MobTraitCap.java:152) |
| dimension (`WorldDifficultyConfig.levelMap`) | same shape | SectionDifficulty.java:62-67 |
| biome (`biomeMap`) | same shape | SectionDifficulty.java:68-69 |
| distance from spawn | `distanceFactor * sqrt(x²+z²)` added to `base` | SectionDifficulty.java:70-71 |
| local section difficulty | adaptive level from kills in this chunk section | SectionDifficulty.java:54-55 |
| player | player level + trait cap + scale attribute + curse bonuses | PlayerDifficulty.apply (PlayerDifficulty.java:107) |

The final roll, `MobDifficultyCollector.getDifficulty(random)`
(MobDifficultyCollector.java:70):

```
mean  = base + difficulty * scale
if any config contributed → mean += gaussian * sqrt(sum of variation²)
mean *= finalFactor
clamp(mean, min, cap)
```

The `apply_chance` and `trait_chance` fields gate *whether* the mob gets scaled/traited at all
(see 4.2); `fullChance` (forced by config or boss/preset paths) forces these to 1.

### 4.2 TraitManager.fill

`TraitManager.fill` (content/logic/TraitManager.java:44) turns the collector into a concrete level:

1. Roll `lv = clampLevel(getDifficulty(random))`.
2. If `apply_chance()` fails → return 0 (mob stays vanilla).
3. If the mob is not tagged `NO_SCALING` → `scale()`: set `MAX_HEALTH` with a permanent
   `MULTIPLY_TOTAL` modifier equal to `(1 + healthFactor)^lv − 1` (or `lv · healthFactor` in linear
   mode), then `× config.healthScale`.
4. If equipment datapack is enabled and the entity is `ARMOR_TARGET` → `ItemPopulator.populateArmors`.
5. If `trait_chance(lv)` passes → `TraitGenerator.generateTraits(...)`. `trait_chance(lv)` ramps with
   level: `trait_chance · min(1, lv · initialTraitChanceSlope)`.

`clampLevel` (MobTraitCap.java:203) caps by `maxMobLevel` config and, if the entity has a config,
its `maxLevel`.

### 4.3 Difficulty scaling (levels rising as you progress)

There are two "adaptive" accumulators that grow from kills:

**Player**: `PlayerDifficulty.difficulty` is a `DifficultyLevel` (level + experience + extraLevel).
`addKillCredit(cap)` (PlayerDifficulty.java:127) is called on mob death:

- Updates `maxRankKilled` (highest trait rank killed; raises the trait-level cap, see §5).
- `difficulty.grow(growFactor, cap)` (DifficultyLevel.java:39): adds `growFactor·lv²` experience,
  then spends it against a `level²·killsPerLevel` cost curve to raise `level`.
- Every 10 player levels it grants a `HOSTILITY_ORB`.

`extraLevel` adds item/attribute and dimension bonuses: `(visitedDimensions − 1)·dimensionFactor +
ADD_LEVEL attribute`. Curse curios can scale the grow factor per kill
(`CurseCurioItem.getGrowFactor`).

**Chunk**: `SectionDifficulty.difficulty` grows by 1 per kill in that 16×16 section
(`addKillHistory`, SectionDifficulty.java:131). The section's level is added to the collector of any
mob spawning there (`allowSectionDifficulty`). Unless the section is `CLEARED` (cleared by a beacon,
which forces `cap = 0` — mobs there stay level 0).

### 4.4 The player-side of the collector

`PlayerDifficulty.apply(instance)` (PlayerDifficulty.java:107) is the *player's* contribution to mob
difficulty, which is the mod's core escalation mechanism:

- `acceptBonus(playerLevel)` — mob level base rises with player level.
- `setTraitCap(getRankCap())` — mobs may roll traits up to a rank derived from what the player has
  killed (see §5.3).
- `scale += ADD_SCALE attribute`.
- Curve-of-pride curio: multiplies trait cost factor + force full chance.
- `ABYSSAL_THORN` curio: trait cost → 0, full chance, full drop.

## 5. Trait generation

`TraitGenerator` (content/logic/TraitGenerator.java) is the whole trait-rolling algorithm. It was
ported from the 1.21 branch and includes the exclusion system.

### 5.1 Inputs

Constructor inputs (TraitGenerator.java:31):

- `cap`, `entity`, `mobLevel`, the `traits` map being built, and the `MobDifficultyCollector`.
- `free` = `trait_cost < 0.01` (all traits at max rank, no budget).
- `maxTrait` = `maxTraitCount / trait_cost` (-1 if free), from entity config or common config.

The **candidate pool** starts as every registered trait passing:

- not in the entity config's `blacklist`, and
- `trait.allow(entity, mobLevel, ins.getMaxTraitLevel())` (MobTrait.java:73):
  - trait not banned (config toggle or missing registration),
  - `mobLevel >= TraitConfig.min_level`,
  - entity not blacklisted from the trait via `EntityConfig.allow` and the trait's own entity tags.

### 5.2 Base / preset traits

For each `EntityConfig.Config.traits()` entry whose `TraitCondition` matches (level gate, chance,
advancement), `genBase(base)` (TraitGenerator.java:109) forces the trait with `free` base rank and
`min` floor, spending from the level budget. Capped base traits are removed from the pool.
`presetTraitsOnly` clears the randomized pool entirely, leaving only preset traits.

### 5.3 The weighted pool and exclusion

After base traits are applied, `TraitPool` (TraitGenerator.java:136) is built over the remaining
candidates:

- Each `TraitEntry` holds `baseWeight = TraitConfig.weight` and a mutable `chance` and `weight`.
- The constructor seeds it with the already-picked traits via `update(trait)` for each, then
  `purge()`s any entry whose weight hit 0.

`update(trait)` (TraitGenerator.java:178) implements exclusivity in **two directions**:

1. **Direction A — the added trait lists targets**: iterate `trait.getExclusion().excluded`; each
   surviving pool trait on that list gets `updateExclusion(rate)`.
2. **Direction B — the pool lists the added trait**: for each surviving pool trait `e`, look up
   `e.getExclusion().getValue(addedTrait)`; if non-zero, apply it.

`updateExclusion(rate)` (TraitGenerator.java:243): `chance *= 1 − rate`,
`weight = (int)(baseWeight·chance)`. So an exclusion of `1` kills the trait (purged at the next
`purge()`); `0.5` halves remaining weight each time it's triggered. Because an entry keeps its own
`chance`, repeated penalties multiply. Note the interaction if **A and B mutually exclude each
other**: whichever is rolled second came out of the pool already, so the surviving one takes both
penalties (`(1−r₁)(1−r₂)`). Shipped defaults never declare both directions.

The `max level` a single trait rank can be rolled at is `min(ins.getMaxTraitLevel(), trait.getMaxLevel())`.
`getMaxTraitLevel()` comes from `MobDifficultyCollector.traitCap`, which is
`min(6, maxRankKilled + 1)` because `PlayerDifficulty.apply` calls `setTraitCap(getRankCap())`
(PlayerDifficulty.java:123-125). This is the **trait-rank cap**: players must kill traits of a rank
to unlock rolling that rank on future mobs.

### 5.4 generate()

`generate()` (TraitGenerator.java:85) is the spending loop:

```
while level > 0 and pool not empty:
    e = pool.pop()                      // weighted random
    cost = e.getCost(trait_cost)
    if cost > level: continue
    max  = min(ins.getMaxTraitLevel(), e.getMaxLevel())
    old  = current rank of e in traits
    rank = free ? max : min(max, old + nextInt(level/cost) + 1)
    if rank <= old: continue
    setRank(e, rank)                     // → pool.update(e) applies exclusions
    level -= (rank-old)*cost
    if not fullChance and random < suppression: break
then each picked trait gets initialize(entity, rank)
```

`setRank` (TraitGenerator.java:66) triggers `pool.update(e)` only when the trait was *not already in
the traits map*, and removes at rank 0. During construction the pool is null, so base traits skip
the exclusion step and are folded in by the pool constructor instead.

## 6. Traits at runtime

### 6.1 Contract

`MobTrait extends NamedEntry<MobTrait>` (content/traits/base/MobTrait.java). Its overridable hooks:

| hook | called from | purpose |
|---|---|---|
| `initialize(mob, lv)` | generator, clearPending | apply attribute modifiers / state (once per rank set) |
| `postInit(mob, lv)` | POST_INIT stage & clearPending | apply effects/equipment after all traits known |
| `tick(mob, lv)` | MobTraitCap.tick | per-tick behavior |
| `onAttackedByOthers` | MobEvents.onMobAttack (`LivingAttackEvent`) | react on the mob being attacked |
| `onHurtByOthers` | MobEvents.onMobHurt (`LivingHurtEvent`) | modify incoming damage/reactions |
| `onHurtTarget(level, attacker, cache, traitCache)` | LHAttackListener.onHurt | when *the mob* hurts something; routes to `postHurtPlayer`/`postHurtImpl` with reflect support |
| `onCreateSource` | LHAttackListener.onCreateSource | customize the damage source the mob creates |
| `onDamaged` | LHAttackListener.onDamage | final damage stage on the mob |
| `onDeath(mob, lv, event)` | MobEvents.onMobDeath + MobTraitCap.onKilled | death behavior (drop/seal/etc) |
| `inherited(cap, rank, ctx)` | copyFrom | adjust rank when a child inherits the trait |
| `modifyBonusDamage(source, factor, lv)` | LHAttackListener.onHurt | multiplier on the mob's level-based damage |

Traits are stored in `MobTraitCap.traits` as a `LinkedHashMap<MobTrait, Integer>` (rank per trait),
serialized with `toClient=true` and sync'ed via `MobCapSyncToClient` on init and on demand
(start-tracking, tick changes).

### 6.2 Tick pipeline

`MobTraitCap.tick` (MobTraitCap.java:263) does, in order:

1. Lazy init if not initialized (chunk → `init`).
2. On the first init tick: `stage = POST_INIT` → `ItemPopulator.postFill` (equipment), `postInit`
   on every trait, apply pending trait mutations, refill HP to full.
3. Prevent un-owner-able traits from sticking to tamed pets (`allowTraitOnOwnable`).
4. Periodic cleanup (`removeTraitInterval`): drop dead/banned traits.
5. `trait.tick` for each trait; process `pending` changes (`clearPending` → initialize + postInit).
6. Master/summoned handling, glow markers, and sync-to-client when anything changed.

`setTrait`/`removeTrait` buffer changes into `pending` while ticking, then `clearPending` applies
them safely after the iteration ends (MobTraitCap.java:228-261).

### 6.3 Trait inheritance

`copyFrom(parent, child, parentCap)` (MobTraitCap.java:170) is used when a mob creates children
(split, master minions, etc.). It copies the level, flags, drop rate (scaled by a split factor), then
runs each trait's `inherited(...)` to compute the child's rank, then re-fills with
`MobDifficultyCollector.noTrait(lv)` — i.e. the child keeps the level but gains no new traits. Marked
`copied = true`.

## 7. Equipment population

`ItemPopulator` (content/logic/ItemPopulator.java) gives leveled mobs gear. It runs at POST_INIT
(`postFill`, ItemPopulator.java:162):

1. **Weapons** — `populateWeapons`: skip Apotheosis bosses/weapons; `special_weapons` (per entity
   set, from `WeaponConfig`) get a weighted pick over matching pools plus an `EMPTY` fallback; else
   `populateSimpleWeapons` picks melee (`MELEE_WEAPON_TARGET` tag) or ranged (`RANGED_WEAPON_TARGET`)
   from `WeaponConfig.melee_weapons`/`ranged_weapons`. Drowned get a trident chance per level.
   Goal attachment uses `mob_weapon_api` (`VanillaMobManager.attachGoal`) so monsters use the tools.
2. **Enchanting** — every slotted item gets a base enchant at
   `lv·enchantmentFactor + upto(30·clamp(lv·0.02,0,1))`; then `fillEnch` applies the config-driven
   `weapon_enchantments`/`armor_enchantments` pools (level-gated, chance-gated, compatibility-safe).
3. **Config items** — entity-specific `ItemPool`s are rolled per slot (weighted), where slots are
   decoded via curios compatibility.

Respects `enableEquipmentDatapack`, `ARMOR_TARGET`, `equipmentDropRate` (mob drop chance), and the
`NO_DROP` behaviors.

`WeaponConfig.getRandomWeapon` (WeaponConfig.java:41) is the generic weighted sampler with
level/player-advancement conditions (`ItemCondition.test`).

## 8. Combat and the damage pipeline

Damage is driven by `l2damagetracker`'s `AttackListener` pipeline, with
`LHAttackListener` (events/LHAttackListener.java) registered at priority 4500. The pipeline has
three stages, each a callback:

### 8.1 onAttack (LivingAttackEvent)

- `masterImmunity(cache)` (LHAttackListener.java:25) cancels attacks between a master and its own
  minions (both directions) and against master-protected mobs (unless the source bypasses
  invulnerability).

### 8.2 onHurt (LivingHurtEvent)

This is the biggest stage:

1. Skip `NO_SCALE` sourced damage and self-damage.
2. Apply `HitTargetEnchantment`s from the weapon on the target.
3. **Level-based damage scaling** for the attacker (LHAttackListener.java:82-103):
   `factor = (1 + damageFactor)^lv − 1` (or `lv·damageFactor` linear), `× config.attackScale`,
   `× Σ trait.modifyBonusDamage(...)`, and `× dispellDamageFactor` if the source bypasses effects.
   Added as an `addHurtModifier(multTotal(1 + factor))`.
4. Build a `TraitEffectCache` for the victim (the collection of "other mortals" for reflect-style
   traits) and run each attacker trait's `onHurtTarget` → `postHurtPlayer` → `postHurtImpl` against
   the victim (with reflect support via `TraitEffectCache.reflectTrait`).
5. Run curse-curio `onHurtTarget` bonuses from the attacker.

### 8.3 onDamage (LivingDamageEvent) and source creation

- All `trait.onDamaged` hooks on the victim.
- `masterImmunity` → `addDealtModifier(nonlinearFinal(... → 0))` zeroes damage.
- `onCreateSource`: traits can retag the source; the `IMAGINE_BREAKER` curio enables
  `BYPASS_MAGIC`, `PLATINUM_STAR` enables `BYPASS_COOLDOWN`.

Outside the tracker, `MobEvents` handles the vanilla events for traits (`onAttackedByOthers`,
`onHurtByOthers`), damage-reduction curios (`onDamage`), death (`onDeath`), drops (`noDrop`,
Nidhoggur multiplier), experience scaling, and potion immunity (curse of wrath).

## 9. Player progression

`PlayerDifficulty` (content/capability/player/PlayerDifficulty.java) is the player cap:

- `difficulty` (DifficultyLevel) — the persistent kill-based level (see §4.3).
- `maxRankKilled`, `rewardCount`, `dimensions` (per-dimension scaling).

`addKillCredit` (PlayerDifficulty.java:127) is the only source of growth:
`difficulty.grow(playerKillCurseFactor, mobCap)`, track `maxRankKilled`, and hand out an orb every
10 player levels. `apply(collector)` (PlayerDifficulty.java:107) injects this into every mob
spawned near the player (§4.1).

`onClone(false)` (on death) applies death decay per config: clear dimension bonuses, decay
`maxRankKilled`, and `difficulty.decay()` — which drops the level by `level·(1 − rate)` and zeroes
experience; all three linear-attribute pairings honor the keep-inventory gamerule.

`getLevelEditor()`/`DifficultyLevel.Editor` expose in-game editing (used by the level editing
commands / dev tools).

## 10. Loot and trait drops

### 10.1 TraitLootModifier

`init/loot/TraitLootModifier.java` is the datapack-driven "trait symbol drop" system. Its JSON
form (registered via `TraitGLMProvider`, generated with a Mojang `Codec`):

```json
{ "type": "l2hostility:trait",
  "trait": "l2hostility:grenade",   // optional: null = any traitful mob
  "chance": 0.15, "rankBonus": 0.05,
  "result": { "item": "l2hostility:trait_symbol", "nbt": "..." },
  "conditions": [...] }
```

`doApply` (TraitLootModifier.java:60):

1. Requires a proper mob and not `NO_DROP`.
2. If a trait is specified, the mob must have it. Drop multiplier = `cap.dropRate` × each
   `CurseCurioItem.getLootFactor` of the killer.
3. Per-result-count droplets, each succeeds with probability `chance + rank·rankBonus` (rank = the
   mob's rank in that trait).

Supporting loot conditions: `TraitLootCondition` (require a trait), `MobCapLootCondition` (min
level), `MobHealthCondition` (min health), `PlayerHasItemCondition` (killer must wear/own an item).
There are also `EnvyLootModifier` and `GluttonyLootModifier` for the curse mascot mechanic.
`TraitLootModifier` implements `ITraitLootRecipe` for JEI and its data is synced to clients via
`LootDataToClient` on `OnDatapackSyncEvent` (MobEvents.java:130-144).

### 10.2 TraitSymbol item

`TraitSymbol` (content/item/traits/TraitSymbol.java) is the collectible token per trait. Right/left
click behaviors apply the trait to mobs (curse-style), and it is the "result" of the loot modifiers.
Items it needs to eat/work are handled by `DurabilityEater`, `EnchantmentDisabler`, `SealedItem`
logic etc.

## 11. Entities, projectiles, effects, enchantments

### 11.1 Projectiles (`content/entity/`)

- `HostilityBullet` (renderer `BulletRenderer`, with a `ShulkerBulletMixin`) — the shulker-style
  projectile. `BulletType.PLAIN` (4 dmg/rank) and `BulletType.EXPLODE` (AoE explosion scaled by
  rank, damage-calculator-immune to explosion for the shooter). Used by the Shulker/Grenade traits.
- `HostilityCharge` (renderer via `SpecialSpriteRenderer`, `ChargeType`) — a larger "charge"
  projectile geometry.

Both are fired by traits (Grenade, etc.) and rendered client-side; the mixins expand vanilla
projectile behavior.

### 11.2 Effects (`content/effect/`)

Custom mob effects registered in `LHEffects`:

- `GravityEffect` (`l2hostility:gravity`) — increase entity gravity (used by `GravityTrait`, moonwalk
  enemies).
- `MoonwalkEffect` (`l2hostility:moonwalk`) — decrease gravity.
- `AntiBuildEffect` (`l2hostility:antibuild`) — players cannot place blocks. (`Gravity`/`Moonwalk`
  also underly `GravityTrait`/`AuraEffectTrait`.)

### 11.3 Enchantments (`content/enchantments/` + `LHEnchantments`)

All extend `HostilityEnchantment extends UnobtainableEnchantment` (not obtainable normally):

- `INSULATOR` (`insulator`) — armor, reduces pull/push trait effects on the wearer.
- `SPLIT_SUPPRESS` (`split_suppressor`) — weapon `RemoveTraitEnchantment` that strips the `split`
  trait from hit mobs (`HitTargetEnchantment.hitMob`).
- `VANISH` (`vanish`) — item vanishes when on the ground or in a survival/adventure player's hand
  (trophy logistics).

## 12. Master & minion system

`EntityConfig.MasterConfig` and `Minion` describe summoners (e.g. `MasterTrait`, and entity configs
that set `asMaster`). Runtime state lives on `MobTraitCap`:

- `asMinion` (`MinionData`) — on the minion: its master reference, link distance, protect flag,
  copy-level/copy-trait flags, despawn-on-unlink.
- `asMaster` (`MasterData`) — on the master: the list of live minions.

`MobTraitCap.tick` drives it (MobTraitCap.java:309-325): minions tick their link (`asMinion.tick`),
and if the mob has `MASTER` trait, a `MasterData` is lazily created and ticked to maintain minion
counts (`asMaster.tick`), with spawn scheduling from the config. `masterImmunity` (§8.1) prevents
masters from hitting their own minions; `isMasterProtected` reports whether a protecting minion is
alive. The client shows the master's minions glowing. Minion drops/level/inheritance use
`copyFrom` (§6.3).

## 13. Items overview

Sketch of the item families (`content/item/`), all registered in `LHItems`:

- **wands** (`wand/`) — `BaseWand`, `EquipmentWand`, `AiConfigWand`, `TargetSelectWand`,
  `TraitAdderWand`, `IMobClickItem` — dev/ops tools to set mob levels, equip, configure AI, and
  grant/remove traits.
- **curio / curses** (`curio/curse/`) — the seven sins (`CurseOf*` extending `CurseCurioItem`,
  core/CurseCurioItem.java) that buff the wearer at a cost and slot into the curse tab. They feed
  difficulty growth (`getGrowFactor`), loot (`getLootFactor`), and attack hooks.
- **curio / misc** (`curio/misc/`) — legendary utility relics: `ImagineBreaker` (bypass magic),
  `PlatinumStar` (bypass cooldown), `AbyssalThorn`, `DivinityCross/Light`, `FlamingThorn`,
  `GreedOfNidhoggur` (drop multiplier), `InfinityGlove`, `LootingCharm`, `OddeyesGlasses`,
  `PocketOfRestoration`, `TripleStripCape`.
- **curio / ring** (`curio/ring/`) — `RingOfDivinity` (magic immunity), `RingOfHealing`, `RingOfLife`,
  `RingOfOcean`, `RingOfReflection`, `RingOfCorrosion`, `RingOfIncarceration`.
- **consumable** (`consumable/`) — `BottleOfCurse`/`BottleOfSanity` (give/clear a curse),
  `DrinkableBottleItem`, `EffectBoosterBottle`, `HostilityOrb` (leveling reward), `HostilityChargeItem`
  (boss-fight ticket), `BookCopy`/`BookEverything`/`BookTrait` (the "book" mechanic of clearing
  traits/difficulty).
- **spawner** (`spawner/`) — `TraitSpawnerBlock*` entity-based spawners with data-driven
  `BaseTraitMethod` (`ClickTraitMethod`, `BurstTraitMethod`); tracked by `MobTraitCap.pos` (placed
  mobs are discarded if the spawner is removed).
- **beacon** (`beacon/`) — `HostilityBeaconBlock*` + menu/screen — clears configured sections
  (uses `SectionDifficulty.setClear`).
- **tool** (`tool/`) — `Detector`, `DetectorGlasses` (visibility), `WitchWand`.
- **traits** (`traits/`) — `TraitSymbol` and the drop/application companions (`DurabilityEater`,
  `EnchantmentDisabler`, `ReprintHandler`, `SealedItem`, `EffectBooster`).

Misc registrations: wrapped player attributes `ADD_LEVEL` (`l2damagetracker.extra_difficulty`) and
`ADD_SCALE` (`extra_scale`) (LHMiscs.java:28-31), `EquipmentsMenu` (see a mob's equipment), and a
`Curios` menu compat.

## 14. The in-game config editor (`editor/`)

The editor is a client-side, in-world datapack editor layered on the same config system. Visible
from any `HostilityHomeScreen`, it has seven tabs (HostilityHomeScreen.java:32-38):

1. **World** → `DifficultyHomeScreen` (WorldDifficultyConfig files)
2. **Traits** → `TraitHomeScreen` / `TraitFileScreen` (TraitConfig files)
3. **Excl** → `TraitExclusionHomeScreen` / `TraitExclusionGridScreen` (TraitExclusion files, edited
   as a per-group icon grid; see doc/editor.md §4)
4. **Weapons** → `WeaponHomeScreen` (WeaponConfig files)
5. **Entities** → `EntityHomeScreen` (EntityConfig files, incl. master/minion/item pools)
6. **Tags** → `TagsHomeScreen` (trait/entity tag files)
7. **Config** → `ConfigHomeScreen` (the Forge `LHConfig` common/client spec sections)

Generic form/list/map screens live in `editor/base/` (copied from ModularGolems, see
`doc/migration.md`); L2Hostility-specific wrappers (`editor/config/`, `editor/home/`) bind them to
the config classes. `LHConfigEdit` (editor/config/LHConfigEdit.java) drives the Forge-config section
forms (`openSectionForm`, `resetToDefault`).

Saving writes a JSON into a world-level datapack; `EditorFile.writePackMeta` maintains
`pack.mcmeta`, and the client triggers a datapack reload so the world picks up the change immediately
(simple JSON files + `SimpleJsonResourceReloadListener` make this work without restart). Editing
Forge-config sections writes to the real spec and leaves an "unsaved reload" flag
(`EditorSaveState.savedFlag`) so the user is reminded to `/reload` before moving on.

This editor is fully described in `doc/editor.md`; only the system connections are summarized here.

## 15. Compat and datagen

### 15.1 Compat (`compat/`)

- **curios** — `CurioCompat` (curios slot/stack access) powers curse/ring/misc items, the `CURIOS`
  menu, and the `decode` slot resolution in `ItemPopulator.generateItems`. Tab/slot registration via
  the curios integration.
- **kubejs** — a KubeJS plugin (`kubejs.plugins.txt`) exposing registration builders
  (e.g. for entities/traits) under `compat/kubejs/`, so scripters can register content without
  Java.
- **jei** — `compat/jei/ITraitLootRecipe` feeds trait-loot drops into JEI as recipes (chance, rank,
  required curios).
- **jade** — `compat/jade/` tooltip providers (mob level/traits overview).
- **gateway** — `GatewayToEternityCompat` + `GatewayConfigGen`: gateways gain hostility difficulty
  and default entity configs when `gateways` is loaded.
- **data/** — per-external-mod default config generators (`TFData`, `CataclysmData`, `BoMDData`,
  `IaFData`, `MutantMonsterData`, `MowzieData`, plus l2complements/l2weaponry/l2archery weapon and
  enchant pools in `LHConfigGen`). All gated on `ModList.get().isLoaded(...)` at datagen time.

### 15.2 Datagen summary

`gatherData` (L2Hostility.java:127) wires:

- Lang (mod + `EditorText` + `HostilityEditorLang`), recipes, advancements.
- Tag generation span many domains: item/block/entity/damage-type/enchant/effect/trait tags
  (`LHTagGen`), plus the custom `TRAIT_TAGS` provider (LHTraits.java:36).
- `TraitGLMProvider` (loot modifier JSONs), `SlotGen`.
- `LHDamageTypes` and `LHConfigGen` — the config JSONs of §3.
- The registrate-generated entries (items, blocks, entities, etc.).

The `build` task reobfs and packages; the generated JSONs are committed
(`src/generated/resources`). **After changing any config default, re-run `./gradlew runData` and
commit the diff.**

## 16. Performance & lifecycle notes

- Mobs only get caps when eligible (`Enemy && !BLACKLIST || WHITELIST`, MobTraitCap.java:53-55) and
  remain *level 0 / no traits* if the gather chances fail — this keeps vanilla mob counts cheap.
- The chunk capability is attached to every `LevelChunk` (CapabilityEvents.java:34); the
  per-section `DifficultyLevel` is tiny and lazily initialized (`ChunkDifficulty.init` allocates the
  sections on first inject).
- Trait ticking is gated on `isInitialized()` and traits being non-empty; a suppression of sync
  happens only when state actually changed (`sync` flag, MobTraitCap.java:263-331).
- NaN health/absorption are force-healed every `NAN_FIX` ticks, and dead/banned traits are purged
  on an interval.
- `PerformanceConstants` centralizes the tick-interval constants (trait sync, NAN_FIX,
  removeTraitInterval).
